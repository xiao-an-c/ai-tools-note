# 需求变更与技术栈更新

## 什么是 Milestone（里程碑）

Milestone 是 GSD 中的版本概念。当一个里程碑的所有阶段完成后，你可以：

1. **归档**当前里程碑的成果
2. **开启**下一个里程碑，定义新的需求
3. **变更**技术栈（视为新需求的一部分）

---

## 完整工作流程

```
┌─────────────────────────────────────────────────────────┐
│                   Milestone 生命周期                      │
├─────────────────────────────────────────────────────────┤
│                                                          │
│   Phase 1 ──► Phase 2 ──► Phase 3 ──► Phase N          │
│   (execute)   (execute)   (execute)                    │
│                                                          │
│                    ↓                                     │
│              /gsd:audit-milestone                      │
│                    ↓                                     │
│          检查所有需求是否完成、是否有遗漏                  │
│                    ↓                                     │
│           /gsd:complete-milestone                      │
│                    ↓                                     │
│         归档里程碑，打 tag，开始下一个                    │
│                                                          │
│                    ↓                                    │
│           /gsd:new-milestone                           │
│                    ↓                                    │
│     新里程碑：提问 → 研究 → 需求 → 路线图               │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

## 场景一：新增需求（第二次需求变更）

### 适用情况

- v1.0 已经完成，想开发 v1.1
- 项目上线后收到新需求
- 想添加之前不在范围内的功能

### 操作步骤

```bash
# 1. 先验证当前里程碑完成度
/gsd:audit-milestone
```

系统会检查：
- 所有阶段是否完成
- 需求是否都有对应实现
- 是否有验证债务

```bash
# 2. 完成当前里程碑
/gsd:complete-milestone
```

这会：
- 归档当前里程碑到 `MILESTONES.md`
- 创建 git tag
- 清理不必要的状态

```bash
# 3. 开启新里程碑
/gsd:new-milestone
```

流程和 `/gsd:new-project` 类似：
1. **提问**：问你想新增什么
2. **研究**：调研新需求的领域
3. **需求**：梳理 v2.0 的功能范围
4. **路线图**：创建新阶段规划

```bash
# 4. 继续正常流程
/gsd:discuss-phase 1
/gsd:plan-phase 1
/gsd:execute-phase 1
/gsd:verify-work 1
```

## 场景二：变更技术栈

### 适用情况

- 想把 React 换成 Vue
- 想从 REST 切换到 GraphQL
- 想更换数据库
- 想引入新的框架

### 重要前提

> **技术栈变更不是小事**。GSD 会把它当作一个新项目来对待，因为技术栈变更会影响所有代码。

### 操作步骤

```bash
# 1. 先完成当前里程碑（如果还没完成）
/gsd:audit-milestone
/gsd:complete-milestone
```

```bash
# 2. 开启新里程碑，明确说明是技术栈变更
/gsd:new-milestone
```

在提问阶段，告诉 GSD：
- 当前技术栈是什么
- 想换成什么
- 为什么需要变更

```bash
# 3. GSD 会自动分析技术栈变更的影响
#    并在研究阶段重点调研：
#    - 新技术栈的迁移路径
#    - 兼容性方案
#    - 风险评估
```

### 技术栈变更的阶段规划

通常技术栈变更会分为多个阶段：

```
Phase 01: 基础设施迁移
  - 新技术栈的脚手架搭建
  - 核心依赖迁移
  - 开发环境配置

Phase 02: 渐进式迁移
  - 按模块逐步迁移
  - 保持新旧系统并行
  - 确保功能不受影响

Phase 03: 旧系统清理
  - 移除旧代码
  - 统一技术规范
  - 文档更新
```

### 注意事项

1. **不要想着一口气换完** - 渐进式迁移更安全
2. **保持功能不变** - 迁移期间不要同时添加新功能
3. **充分测试** - 每个阶段都要验证功能正常

## 场景三：修复上线后发现的问题

```bash
# 如果是小问题，用快速模式
/gsd:quick "修复登录页面的样式问题"
```

```bash
# 如果是较大的问题，创建新阶段
/gsd:insert-phase 1.5
```

这会在阶段 1 和 2 之间插入一个新阶段来处理紧急修复。

---

## 场景四：需求变更但不想开新里程碑

有时候只是小的调整，不需要完整的里程碑流程：

```bash
# 在当前里程碑追加阶段
/gsd:add-phase
```

```bash
# 或者用快速模式处理
/gsd:quick "添加用户头像上传功能"
```

---

## 命令速查

| 场景 | 命令 |
|------|------|
| 开启新里程碑 | `/gsd:new-milestone` |
| 完成当前里程碑 | `/gsd:complete-milestone` |
| 检查里程碑完成度 | `/gsd:audit-milestone` |
| 查看当前进度 | `/gsd:progress` |
| 在阶段间插入新阶段 | `/gsd:insert-phase 1.5` |
| 追加阶段到末尾 | `/gsd:add-phase` |
| 快速修复/小需求 | `/gsd:quick` |

---

## 决策指南

```
需求变更 → 多大？
    │
    ├── 小改动（如添加一个字段）→ /gsd:quick
    │
    ├── 单阶段任务 → /gsd:add-phase
    │
    └── 新增功能模块/技术栈变更 → /gsd:new-milestone
```
