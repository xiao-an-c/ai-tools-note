# GSD 上下文工程原理

## 什么是 Context Rot（上下文腐烂）

**Context Rot** 是 AI 编程助手的一个根本性问题：

随着对话进行，AI 的上下文窗口被填满，输出质量会逐步劣化。

### 表现形式

1. **遗忘早期信息** - 忘记项目约束、已做决策
2. **输出变得冗长** - "我会更简洁一些"的退化状态
3. **重复劳动** - 做已经做过的事情
4. **质量下降** - 代码质量变差，逻辑错误增多

### 根本原因

```
┌─────────────────────────────────────────────────────────┐
│  上下文窗口 (200K tokens)                                │
├─────────────────────────────────────────────────────────┤
│  [早期对话] [中期对话] [近期对话] [当前任务]              │
│                                                          │
│  ↓ 随着对话增长                                          │
│                                                          │
│  [早期...中...后...最...当]  ← 信息密度下降              │
│                                                          │
│  AI 开始"变笨"                                           │
└─────────────────────────────────────────────────────────┘
```

## GSD 的解决方案

### 1. 文件化状态（File-Based State）

所有状态都以**人类可读的文件**形式存储：

```
.planning/
├── PROJECT.md      # 项目愿景（始终加载）
├── STATE.md        # 当前状态（跨会话记忆）
├── ROADMAP.md      # 路线图
└── phases/         # 阶段规划
```

**好处**：
- 状态在 `/clear` 后依然存在
- 人类可以检查和修改
- 可以提交到 git 供团队共享

### 2. 新上下文执行（Fresh Context Execution）

每个执行代理获得**全新的 200K token 上下文**：

```
Orchestrator (主上下文，保持轻量)
    │
    ├── Executor 1 (全新 200K 上下文)
    │   └── 只加载：PLAN.md + PROJECT.md + STATE.md
    │
    ├── Executor 2 (全新 200K 上下文)
    │   └── 只加载：PLAN.md + PROJECT.md + STATE.md
    │
    └── Executor 3 (全新 200K 上下文)
        └── 只加载：PLAN.md + PROJECT.md + STATE.md
```

**好处**：
- 执行质量始终如一
- 不受历史对话污染
- 每个任务都有充足的上下文空间

### 3. 原子化任务（Atomic Tasks）

每个计划足够小，可以在一个全新上下文中完成：

```xml
<task type="auto">
  <name>Create login endpoint</name>
  <files>src/app/api/auth/login/route.ts</files>
  <action>
    Use jose for JWT.
    Validate credentials.
    Return httpOnly cookie.
  </action>
  <verify>curl -X POST localhost:3000/api/auth/login</verify>
</task>
```

**好处**：
- 任务边界清晰
- 验证标准明确
- 失败易于定位

### 4. 轻量编排器（Thin Orchestrators）

编排器本身不做重活，只负责：

```
Orchestrator
    │
    ├── 1. 加载必要的上下文
    │
    ├── 2. 派发专用代理
    │
    ├── 3. 等待结果
    │
    ├── 4. 整合结果
    │
    └── 5. 更新状态文件
```

**好处**：
- 主上下文始终保持轻量
- 编排器可以持续工作
- 真正的工作发生在子代理中

## 设计原则

### 1. Absent = Enabled

配置遵循"缺失即启用"原则：
- 如果配置项不存在，默认为 `true`
- 用户显式禁用功能，而不是启用

```json
{
  "workflow": {
    "research": true,      // 可以省略，默认 true
    "plan_check": false    // 显式禁用
  }
}
```

### 2. 防御深度

多层保护防止失败：

```
Plan Check → 执行前验证计划
    ↓
Atomic Commit → 每个任务独立提交
    ↓
Verification → 执行后验证结果
    ↓
UAT → 人工验收测试
```

### 3. 状态隔离

- 主会话状态存在 `STATE.md`
- 阶段状态存在 `phases/XX/`
- 研究状态存在 `research/`

每个阶段的状态相互独立，互不污染。

## 上下文监控

GSD 通过 Hook 监控上下文使用量：

| 剩余上下文 | 级别 | 建议行为 |
|-----------|------|----------|
| > 35% | 正常 | 无警告 |
| ≤ 35% | 警告 | 避免开始新的复杂工作 |
| ≤ 25% | 严重 | 上下文即将耗尽，通知用户 |

---

## 为什么这很重要

### 传统模式的失败

```
用户: 帮我构建一个完整的应用
AI: 好的，让我开始...
    [大量对话...]
    [上下文填满...]
    [AI 开始"变笨"...]
    [代码质量下降...]
    [最终失败或需要重新开始]
```

### GSD 模式的成功

```
用户: /gsd:new-project
GSD: [提问] [研究] [规划]
     生成 ROADMAP.md

用户: /gsd:execute-phase 1
GSD: [派发 Executor 1 - 全新上下文]
     [派发 Executor 2 - 全新上下文]
     [派发 Executor 3 - 全新上下文]
     每个执行质量一致
```

## 总结

GSD 的上下文工程解决了一个根本问题：

**如何在保持 AI 输出质量的同时，完成复杂的多步骤任务？**

答案是：
1. **文件化状态** - 让记忆持久化
2. **新上下文执行** - 让每个任务都有充足空间
3. **原子化任务** - 让任务边界清晰
4. **轻量编排** - 让主会话保持响应

这样，无论项目多复杂，每个执行步骤都能获得与开始时相同的质量。
