# 核心工作流

GSD 的核心是一个循环：**讨论 → 规划 → 执行 → 验证**

```
┌─────────────────────────────────────────────────────────┐
│                    GSD 工作流                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   /gsd:discuss-phase ──→ /gsd:plan-phase ──→           │
│        ↓                        ↓                       │
│   收集决策                 研究并制定计划                  │
│        ↓                        ↓                       │
│   CONTEXT.md              PLAN.md + RESEARCH.md         │
│                                 ↓                       │
│                          /gsd:execute-phase             │
│                                 ↓                       │
│                           并行执行任务                    │
│                                 ↓                       │
│                          /gsd:verify-work               │
│                                 ↓                       │
│                           人工验收测试                    │
│                                 ↓                       │
│                          重复或完成里程碑                  │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

## 1. 初始化项目

```bash
/gsd:new-project
```

一个命令，完成整个初始化流程：

1. **提问**：问到彻底理解你的想法
2. **研究**：并行调研领域知识（可选但推荐）
3. **需求梳理**：提取 v1、v2 范围
4. **路线图**：创建阶段规划

**生成文件：**
- `PROJECT.md` - 项目愿景
- `REQUIREMENTS.md` - 需求文档
- `ROADMAP.md` - 路线图
- `STATE.md` - 当前状态
- `.planning/research/` - 研究资料

## 2. 讨论阶段

```bash
/gsd:discuss-phase 1
```

**这是你塑造实现方式的地方。**

路线图里每个阶段通常只有一两句话。这一步把你的偏好收进去。

系统会分析该阶段并识别灰区：
- **视觉功能**：布局、交互、空状态
- **API / CLI**：返回格式、错误处理
- **内容系统**：结构、语气、深度

**生成文件：** `{phase_num}-CONTEXT.md`

::: tip 为什么要讨论
你在这里给出的信息越具体，系统越能构建出你真正想要的东西。跳过它，拿到的是合理默认值；用好它，拿到的是 **你的** 方案。
:::

## 3. 规划阶段

```bash
/gsd:plan-phase 1
```

系统会：

1. **研究**：结合你的决策，调研实现方式
2. **制定计划**：创建 2-3 份原子化任务计划
3. **验证**：将计划与需求对照检查

每份计划都足够小，可以在一个全新的上下文窗口里执行。没有质量衰减。

**生成文件：**
- `{phase_num}-RESEARCH.md`
- `{phase_num}-{N}-PLAN.md`

## 4. 执行阶段

```bash
/gsd:execute-phase 1
```

系统会：

1. **按 wave 执行计划**：能并行的并行，有依赖的顺序执行
2. **每个计划使用新上下文**：20 万 token 纯用于实现
3. **每个任务单独提交**：原子化 git commit
4. **对照目标验证**：检查是否真的交付了承诺的内容

```
┌─────────────────────────────────────────────────────────┐
│  WAVE 1 (parallel)     WAVE 2 (parallel)     WAVE 3     │
│  ┌─────────┐┌─────────┐ ┌─────────┐┌─────────┐┌───────┐ │
│  │ Plan 01 ││ Plan 02 │→│ Plan 03 ││ Plan 04 │→│Plan 05│ │
│  │ User    ││ Product │ │ Orders  ││ Cart    ││Checkout│ │
│  │ Model   ││ Model   │ │ API     ││ API     ││ UI    │ │
│  └─────────┘└─────────┘ └─────────┘└─────────┘└───────┘ │
└─────────────────────────────────────────────────────────┘
```

**生成文件：**
- `{phase_num}-{N}-SUMMARY.md`
- `{phase_num}-VERIFICATION.md`

## 5. 验证工作

```bash
/gsd:verify-work 1
```

**这是你确认它是否真的可用的地方。**

系统会：

1. **提取可测试的交付项**：你现在应该能做到什么
2. **逐项带你验证**："能否用邮箱登录？"
3. **自动诊断失败**：拉起 debug 代理定位根因
4. **创建修复计划**：可立刻重新执行

**生成文件：** `{phase_num}-UAT.md`

## 6. 循环与完成

```bash
# 重复下一个阶段
/gsd:discuss-phase 2
/gsd:plan-phase 2
/gsd:execute-phase 2
/gsd:verify-work 2

# 或者让 GSD 自动判断下一步
/gsd:next

# 所有阶段完成后，创建 PR
/gsd:ship

# 完成里程碑
/gsd:complete-milestone

# 开始下一个版本
/gsd:new-milestone
```

## 快速模式

对于不需要完整规划的临时任务：

```bash
/gsd:quick
```

快速模式保留 GSD 的核心保障（原子提交、状态跟踪），但路径更短。

**参数：**
- `--discuss`：规划前先轻量讨论
- `--research`：规划前调研
- `--full`：启用计划检查和验证
