# Harness 设计：长时间运行应用开发（译文）

> 原文：[Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps) — 作者 Prithvi Rajasekaran，Anthropic Labs 团队

---

过去几个月，我一直在解决两个相互关联的问题：让 Claude 产出高质量的前端设计，以及让它在没有人类干预的情况下构建完整应用。这项工作起源于我们之前在前端设计技能和长时间运行编码代理框架方面的努力——通过提示工程和 harness 设计，我和同事将 Claude 的表现提升到了远超基线的水平，但两者最终都遇到了天花板。

为了突破瓶颈，我寻找了一种在两个截然不同领域都适用的 AI 工程新方法——一个领域由主观审美定义，另一个由可验证的正确性和可用性定义。受到生成对抗网络（GAN）的启发，我设计了一个包含**生成器**和**评估器**的多智能体架构。要构建一个能可靠评分且有品位的评估器，首先需要制定一套标准，把"这个设计好不好"这样的主观判断转化为具体的、可评分的条目。

随后，我将这些技术应用到长时间自主编码中，从之前的 harness 工作中带走了两个经验：将构建分解为可管理的块，以及使用结构化产物在会话之间传递上下文。最终成果是一个三智能体架构——规划器、生成器和评估器——能在数小时的自主编码会话中产出丰富的全栈应用。

## 为什么简单方案不够用

我们之前已经展示过，harness 设计对长时间运行的代理编码效果有重大影响。在早期实验中，我们用一个初始化代理将产品规格分解为任务列表，编码代理每次实现一个功能，然后通过产物传递来在会话间保持上下文。更广泛的开发者社区也收敛到了类似的洞察，比如使用钩子或脚本让代理持续迭代的"Ralph Wiggum"方法。

但一些问题仍然持续存在。对于更复杂的任务，代理仍然倾向于随时间推移偏离正轨。在分解这个问题时，我们观察到代理执行这类任务时有两个常见的失败模式。

第一个是，**模型在长任务中会随着上下文窗口填满而失去连贯性**（参见我们关于上下文工程的文章）。有些模型还会表现出"**上下文焦虑**"——当接近自认为的上下文限制时，开始过早收尾工作。**上下文重置**——完全清空上下文窗口并启动一个新代理，结合结构化交接来携带前一个代理的状态和下一步——可以同时解决这两个问题。

这不同于压缩（compaction），压缩是在原地总结对话的早期部分，让同一个代理在缩短的历史上继续工作。虽然压缩保持了连续性，但它没有给代理一个全新的开始，这意味着上下文焦虑可能仍然存在。重置提供了全新的开始，代价是交接产物需要有足够的状态让下一个代理能干净地接手工作。在我们早期的测试中，发现 Claude Sonnet 4.5 的上下文焦虑严重到仅靠压缩不足以实现良好的长任务表现，因此上下文重置成为 harness 设计中不可或缺的部分。这解决了核心问题，但也增加了编排复杂性、token 开销和每次 harness 运行的延迟。

第二个问题我们之前没有讨论过，那就是**自我评估**。当被要求评估自己产出的工作时，代理倾向于自信地称赞工作——即使对人类观察者来说质量明显平庸。这个问题在主观任务（如设计）中尤为突出，因为没有等同于可验证软件测试的二元检查。布局感觉精致还是普通是一个判断，而代理在给自己的工作打分时可靠地偏向正面。

然而，即使在有可验证结果的任务上，代理有时仍然表现出影响任务完成质量的糟糕判断。**将做工作的代理与评判工作的代理分离开来，是解决这个问题的强有力手段。** 这种分离本身并不能立即消除宽容度；评估器仍然是一个倾向于对 LLM 生成输出慷慨的 LLM。但是，调优一个独立的评估器使其持怀疑态度，远比让生成器对自己的工作苛刻要可行得多。一旦外部反馈存在，生成器就有了一些具体的东西可以作为迭代目标。

## 前端设计：让主观质量可评分

我先在前端设计上进行实验，自我评估问题在这里最为明显。没有任何干预的情况下，Claude 通常会倾向于安全、可预测的布局——技术上功能正常，但视觉上毫不起眼。

两个洞察塑造了我为前端设计构建的 harness。首先，虽然美学不能完全简化为一个分数——个人品味总是会有差异——但它们可以通过编码设计原则和偏好的评分标准来改善。"这个设计美吗？"很难一致地回答，但"这个设计是否遵循了我们的设计原则？"给了 Claude 一些具体可评分的标准。其次，通过将前端生成与前端评分分离，我们可以创建一个驱动生成器产出更强输出的反馈循环。

带着这些想法，我写了四个评分标准，同时提供给生成器和评估器代理：

- **设计质量**：设计是否感觉像一个协调的整体而非部件的集合？好的作品意味着颜色、排版、布局、图像和其他细节组合在一起，创造出独特的基调和身份。
- **原创性**：是否有自定义决策的证据，还是模板布局、库默认值和 AI 生成模式？人类设计师应该能认出深思熟虑的创意选择。未修改的库存组件——或 AI 生成的明显标志如白色卡片上的紫色渐变——在这里会失败。
- **工艺**：技术执行：排版层级、间距一致性、色彩和谐、对比度。这是能力检查而非创意检查。大多数合理的实现默认就能做得不错；失败意味着基本功出了问题。
- **功能性**：独立于美学的可用性。用户能否理解界面的功能，找到主要操作，并在不猜测的情况下完成任务？

我强调设计质量和原创性，弱化工艺术和功能性。Claude 在工艺和功能性上默认就得分不错，因为所需的技术能力往往自然而然地具备。但在设计和原创性上，Claude 的产出往好了说是平淡无奇。评分标准明确惩罚了高度通用的"AI 废话"模式，通过更重地加权设计和原创性，推动模型在审美上更多地冒险。

我使用带详细分数分解的少样本示例来校准评估器。这确保了评估器的判断与我的偏好一致，并减少了跨迭代的分数漂移。

我在 Claude Agent SDK 上构建了这个循环，这让编排保持简单。生成器代理首先根据用户提示创建 HTML/CSS/JS 前端。我给评估器提供了 Playwright MCP，让它能在评分每个标准并撰写详细批评之前直接与实时页面交互。在实践中，评估器会自己导航页面、截图并仔细研究实现后再产出评估。该反馈作为下一次迭代的输入流回生成器。我每次生成运行 5 到 15 次迭代，每次迭代通常将生成器推向更独特的方向，因为它响应评估器的批评。由于评估器是主动导航页面而非评分静态截图，每个周期需要真实的挂钟时间。完整运行长达四小时。我还指示生成器在每次评估后做战略决策：如果分数趋势良好则精修当前方向，如果方法不奏效则转向完全不同的审美。

在多次运行中，评估器的评估随迭代改进后趋于平台期，仍有提升空间。有些生成是渐进式精修的。另一些则在迭代间出现急剧的审美转向。

评分标准的措辞以我没有完全预料到的方式引导了生成器。包含"最好的设计应该是博物馆级别的"这样的短语将设计推向了特定的视觉趋同，表明与标准相关的提示措辞直接塑造了输出的特征。

虽然分数总体上随迭代改进，但模式并不总是干净地线性。后期实现作为一个整体往往更好，但我经常看到我更喜欢中间迭代而非最后一个的情况。实现复杂性也倾向于在轮次间增加，生成器在响应评估器反馈时寻求更雄心勃勃的解决方案。即使在第一次迭代中，输出就明显优于没有任何提示的基线，表明标准及相关语言本身就在评估器反馈导致进一步精修之前，将模型从通用默认值引导开了。

在一个引人注目的例子中，我提示模型为一家荷兰艺术博物馆创建网站。到第九次迭代时，它产出了一个虚构博物馆的干净、深色主题落地页。页面视觉精致，但很大程度上符合我的预期。然后，在第十个周期中，它完全废弃了这种方法，将网站重新想象为一种空间体验：一个用 CSS 透视渲染的棋盘格地板 3D 房间，以自由形式位置挂在墙上的艺术品，以及基于门洞的画廊房间导航，而不是滚动或点击。这是我在单次生成中从未见过的创意飞跃。

## 扩展到全栈编码

有了这些发现，我将这种受 GAN 启发的模式应用到全栈开发中。生成器-评估器循环自然地映射到软件开发生命周期上，代码审查和 QA 在其中扮演与设计评估器相同的结构角色。

### 架构

在我们早期的长时间运行 harness 中，我们通过初始化代理、每次处理一个功能的编码代理和会话间的上下文重置解决了连贯的多会话编码。上下文重置是一个关键解锁：harness 使用的是 Sonnet 4.5，它表现出前面提到的"上下文焦虑"倾向。创建一个在上下文重置间良好工作的 harness 是保持模型在任务上的关键。Opus 4.5 在很大程度上自行消除了这种行为，所以我能够从这个 harness 中完全去掉上下文重置。代理作为一次连续会话运行整个构建过程，由 Claude Agent SDK 的自动压缩处理上下文增长。

在这项工作中，我在原始 harness 的基础上构建了一个三代理系统，每个代理解决了我在之前运行中观察到的特定差距：

**规划器（Planner）**：我们之前的长时间运行 harness 要求用户预先提供详细的规格。我想自动化这一步，所以我创建了一个规划器代理，它接受简单的 1-4 句提示并将其扩展为完整的产品规格。我提示它在范围上要雄心勃勃，并专注于产品上下文和高层技术设计，而非详细的技术实现。这个强调是因为担心如果规划器试图预先指定粒度的技术细节并弄错了什么，规格中的错误会级联到下游实现。约束代理要交付什么，让他们在工作中自己找到路径，似乎更聪明。我还要求规划器寻找将 AI 功能编织到产品规格中的机会。

**生成器（Generator）**：早期 harness 中的一次一个功能的方法在范围管理上效果很好。我在这里应用了类似的模型，指示生成器以冲刺方式工作，每次从规格中取一个功能。每个冲刺使用 React、Vite、FastAPI 和 SQLite（后来是 PostgreSQL）技术栈实现应用，生成器被指示在每个冲刺结束时自我评估工作，然后交接给 QA。它还有 git 用于版本控制。

**评估器（Evaluator）**：早期 harness 的应用通常看起来令人印象深刻，但当你真正尝试使用时仍然有真正的 bug。为了捕获这些，评估器使用 Playwright MCP 像用户一样点击运行中的应用，测试 UI 功能、API 端点和数据库状态。然后根据它发现的 bug 和一组从前端实验改编的标准对每个冲刺评分，这里覆盖产品深度、功能性、视觉设计和代码质量。每个标准都有一个硬阈值，如果任何一个低于阈值，冲刺就失败，生成器会收到关于出了什么问题的详细反馈。

在每个冲刺之前，生成器和评估器协商一个冲刺合同：在任何代码编写之前，就这一块工作的"完成"是什么样的达成一致。这之所以存在，是因为产品规格是有意保持高层的，我想要一个步骤来填补用户故事和可测试实现之间的差距。生成器提议它要构建什么以及如何验证成功，评估器审查该提案以确保生成器在构建正确的东西。两者迭代直到达成一致。

通信通过文件处理：一个代理写文件，另一个代理读取并在该文件内或用新文件响应，前一个代理再依次读取。生成器然后按照商定的合同构建，再将工作交接给 QA。这让工作忠实于规格，而不会过早过度指定实现。

### 运行 Harness

对于这个 harness 的第一个版本，我使用 Claude Opus 4.5，将用户提示同时运行在完整 harness 和单代理系统上进行比较。我使用 Opus 4.5，因为这是我们开始这些实验时最好的编码模型。

我写了以下提示来生成一个复古视频游戏制作器：

> *Create a 2D retro game maker with features including a level editor, sprite editor, entity behaviors, and a playable test mode.*

下表显示了 harness 类型、运行时长和总成本。

| Harness | 时长 | 成本 |
|---------|------|------|
| 单独运行 | 20 分钟 | $9 |
| 完整 Harness | 6 小时 | $200 |

Harness 贵了 20 倍以上，但输出质量的差异立刻就显而易见了。

我期望的界面是：可以构建关卡及其组成部分（精灵、实体、瓦片布局），然后点击播放来实际玩关卡。我先打开了单独运行的输出，初始应用看起来符合这些期望。

然而，当我点击进入时，问题开始浮现。布局浪费空间，固定高度的面板让大部分视口空白。工作流很僵硬。尝试填充关卡时提示我先创建精灵和实体，但 UI 中没有任何东西引导我走向这个序列。更重要的是，实际的游戏是坏的。我的实体出现在屏幕上但没有任何东西响应输入。深入代码发现实体定义和游戏运行时之间的连接断了，表面上没有任何迹象指出问题在哪。

评估完单独运行后，我转向了 harness 运行。这次运行从同样的一句话提示开始，但规划器步骤将提示扩展为跨越十个冲刺的 16 个功能规格。它远超单独运行尝试的范围。除了核心编辑器和播放模式外，规格还要求精灵动画系统、行为模板、音效和音乐、AI 辅助精灵生成器和关卡设计师，以及带可分享链接的游戏导出。我给规划器访问了我们前端设计技能的权限，它阅读并使用它作为规格的一部分为应用创建了视觉设计语言。对于每个冲刺，生成器和评估器协商了定义冲刺具体实现细节和可测试行为的合同。

应用立即显示出比单独运行更多的精致和流畅。画布使用全视口，面板大小合理，界面有一致的视觉风格，跟踪规格中的设计方向。我在单独运行中看到的一些笨拙确实仍然存在——工作流仍然没有让你清楚应该先构建精灵和实体再尝试填充关卡，我不得不通过摸索来发现这一点。这读起来像是基础模型产品直觉的差距，而非 harness 设计要解决的问题，尽管它确实暗示了一个有针对性的 harness 内迭代可以进一步改善输出质量的地方。

在编辑器中工作时，新运行相比单独运行的优势变得更加明显。精灵编辑器更丰富、功能更全，有更干净的工具调色板、更好的颜色选择器和更可用的缩放控件。

因为我要求规划器将 AI 功能编织到规格中，应用还带有内置的 Claude 集成，让我能通过提示生成游戏的不同部分。这显著加速了工作流。

最大的区别在播放模式。我真的能够让我的实体移动并玩游戏。物理有一些粗糙的边缘——我的角色跳上平台但最终与它重叠，直觉上感觉不对——但核心的东西能工作，这是单独运行没能做到的。移动了一段时间后，我确实遇到了 AI 游戏关卡构建的一些限制。有一堵大墙我跳不过去，所以我卡住了。这表明有一些常识性改进和边缘情况 harness 可以处理来进一步精修应用。

阅读日志时，评估器明显让实现与规格保持一致。每个冲刺，它走查冲刺合同的测试标准，通过 Playwright 操作运行中的应用，对任何偏离预期行为的地方提出 bug。合同是细粒度的——仅 Sprint 3 就有 27 个覆盖关卡编辑器的标准——评估器的发现足够具体，无需额外调查就可以采取行动。下表显示了我们评估器识别的几个问题示例：

| 合同标准 | 评估器发现 |
|----------|-----------|
| 矩形填充工具允许点击拖拽以选中瓷砖填充矩形区域 | **失败** — 工具只在拖拽起点/终点放置瓷砖而非填充区域。`fillRectangle` 函数存在但未在 mouseUp 时正确触发。 |
| 用户可以选择和删除已放置的实体出生点 | **失败** — `LevelEditor.tsx:892` 的删除键处理器需要 `selection` 和 `selectedEntityId` 同时设置，但点击实体只设置了 `selectedEntityId`。条件应为 `selection \|\| (selectedEntityId && activeLayer === 'entity')`。 |
| 用户可以通过 API 重排动画帧 | **失败** — `PUT /frames/reorder` 路由定义在 `/{frame_id}` 路由之后。FastAPI 将 'reorder' 匹配为 frame_id 整数并返回 422："unable to parse string as an integer." |

让评估器达到这个水平需要付出努力。开箱即用时，Claude 是一个糟糕的 QA 代理。在早期运行中，我看到它识别出合理的问题，然后说服自己这些问题不是什么大不了的，反正批准了工作。它还倾向于浅层测试，而非深入边缘情况，所以更微妙的 bug 经常溜过去。调优循环是阅读评估器的日志，找到它的判断与我的分歧的例子，更新 QA 提示来解决这些问题。经过几轮这样的开发循环，评估器才以一种我认为合理的方式评分。即便如此，harness 输出仍然显示了模型 QA 能力的局限性：小的布局问题，某些地方感觉不直观的交互，以及评估器没有充分测试的更深层嵌套功能中未发现的 bug。显然还有更多的验证空间可以通过进一步调优来捕获。但与单独运行相比——应用的核心功能根本不工作——提升是显而易见的。

### 迭代 Harness

第一组 harness 结果令人鼓舞，但它也笨重、缓慢且昂贵。合乎逻辑的下一步是找到在不降低性能的情况下简化 harness 的方法。这部分是常识，部分是一个更一般原则的体现：harness 中的每个组件都编码了一个关于模型自己做不到什么的假设，这些假设值得压力测试，既因为它们可能不正确，也因为它们可能随着模型改进而迅速过时。我们的博文"Building Effective Agents"将底层思想框架为"找到尽可能简单的解决方案，仅在需要时才增加复杂度"，这是任何维护代理 harness 的人都会一致看到的模式。

在我第一次简化的尝试中，我大幅削减了 harness 并尝试了一些有创意的新想法，但我无法复制原始版本的性能。也很难判断 harness 设计的哪些部分实际上是承重的，以及以什么方式。基于那次经验，我转向了更系统的方法，一次移除一个组件并审查对最终结果的影响。

在我进行这些迭代周期时，我们还发布了 Opus 4.6，这为进一步减少 harness 复杂性提供了额外动力。有充分的理由预期 4.6 比 4.5 需要更少的脚手架。我们发布博文说："[Opus 4.6] 计划更仔细，能更长时间地持续代理任务，能在更大的代码库中更可靠地操作，并具有更好的代码审查和调试技能来捕获自己的错误。"它还在长上下文检索上大幅改进。这些都是 harness 一直在补充的能力。

### 移除 Sprint 结构

我先完全移除了冲刺结构。冲刺结构曾帮助将工作分解为模型可连贯处理的块。鉴于 Opus 4.6 的改进，有充分理由相信模型可以原生处理这项工作而无需这种分解。

我保留了规划器和评估器，因为每个都继续增加明显的价值。没有规划器，生成器低估范围：给定原始提示，它会不经规划就先开始构建，最终创建的应用不如规划器那样功能丰富。

移除冲刺结构后，我将评估器改为在运行结束时单次通过，而非每个冲刺评分。由于模型更强大了，它改变了评估器在某些运行中的承重程度，其有用性取决于任务相对于模型可靠独立完成能力的位置。在 4.5 上，那个边界很近：我们的构建处于生成器能单独做好的边缘，评估器在整个构建中捕获了有意义的问题。在 4.6 上，模型的原始能力增加了，边界向外移动。过去需要评估器检查才能连贯实现的任务现在通常在生成器单独处理的能力范围内，对于那个边界内的任务，评估器变成了不必要的开销。但对于构建中仍然处于生成器能力边缘的部分，评估器继续提供真正的提升。

实际含义是，评估器不是一个固定的有或没有的决策。当任务超出当前模型可靠独立完成的范围时，它是值得付出成本的。

在结构简化的同时，我还添加了提示来改善 harness 如何将 AI 功能构建到每个应用中，特别是让生成器构建一个合适的代理，可以通过工具驱动应用自身的功能。这需要真正的迭代，因为相关知识足够新，Claude 的训练数据覆盖得很薄。但经过足够的调优，生成器正确地构建了代理。

### 更新 Harness 的结果

为了测试更新后的 harness，我使用以下提示生成一个数字音频工作站（DAW），一个用于作曲、录制和混音的音乐制作程序：

> *Build a fully featured DAW in the browser using the Web Audio API.*

运行仍然漫长且昂贵，约 4 小时和 124 美元的 token 成本。

大部分时间花在构建器上，它在没有 Opus 4.5 需要的冲刺分解的情况下连贯运行了两个多小时。

| 代理与阶段 | 时长 | 成本 |
|-----------|------|------|
| 规划器 | 4.7 分钟 | $0.46 |
| 构建（第 1 轮）| 2 小时 7 分钟 | $71.08 |
| QA（第 1 轮）| 8.8 分钟 | $3.24 |
| 构建（第 2 轮）| 1 小时 2 分钟 | $36.89 |
| QA（第 2 轮）| 6.8 分钟 | $3.09 |
| 构建（第 3 轮）| 10.9 分钟 | $5.88 |
| QA（第 3 轮）| 9.6 分钟 | $4.06 |
| **V2 Harness 总计** | **3 小时 50 分钟** | **$124.70** |

与之前的 harness 一样，规划器将一行提示扩展为完整规格。从日志中，我可以看到生成器模型在规划应用和代理设计、连接代理并在交接给 QA 之前测试它方面做得很好。

话虽如此，QA 代理仍然捕获了真实的差距。在第一轮反馈中，它指出：

> 这是一个设计保真度出色、AI 代理扎实、后端良好的强应用。主要失败点是功能完整性——虽然应用看起来令人印象深刻，AI 集成工作良好，但几个核心 DAW 功能是仅显示的，没有交互深度：音轨不能在时间线上拖动/移动，没有乐器 UI 面板（合成器旋钮、鼓垫），也没有视觉效果编辑器（EQ 曲线、压缩器仪表）。这些不是边缘情况——它们是让 DAW 可用的核心交互，规格明确要求了它们。

在第二轮反馈中，它再次捕获了几个功能性差距：

> 剩余差距：
> - 音频录制仍然只是存根（按钮切换但没有麦克风捕获）
> - 音轨边缘拖拽调整大小和音轨分割未实现
> - 效果可视化是数字滑块，非图形化的（没有 EQ 曲线）

生成器在无人监督时仍然容易遗漏细节或将功能做成存根，QA 在捕获那些最后一英里问题让生成器修复方面仍然增加了价值。

基于提示，我期望的是一个可以创建旋律、和声和鼓点模式，将它们编排成歌曲，并在此过程中从集成代理获得帮助的程序。最终应用远非专业的音乐制作程序，代理的歌曲作曲技能显然还需要大量工作。此外，Claude 实际上无法听到，这使 QA 反馈循环在音乐品味方面不那么有效。

但最终应用具备了功能性音乐制作程序的所有核心部分：在浏览器中运行的工作编排视图、混音器和传输控制。除此之外，我能够完全通过提示拼凑一个短歌曲片段：代理设置了节奏和调性、编排旋律、构建鼓轨道、调整混音器级别并添加了混响。歌曲作曲的核心原语已存在，代理可以自主驱动它们，使用工具从头到尾创建一个简单的制作。你可能会说它还不完美——但它正在接近。

## 接下来是什么

随着模型持续改进，我们可以粗略预期它们能够工作更长时间、处理更复杂的任务。在某些情况下，这意味着围绕模型的脚手架随时间推移变得不那么重要，开发者可以等待下一个模型看到某些问题自行解决。另一方面，模型变得越好，就有越多的空间来开发能够实现超出模型基线能力的复杂任务的 harness。

考虑到这一点，这项工作中有一些值得延续的经验。始终对你要构建的模型进行实验、在现实问题上阅读它的轨迹、并调优其性能以实现期望的结果，这是好的实践。在处理更复杂的任务时，有时通过分解任务并将专门的代理应用于问题的每个方面，可以获得提升空间。当新模型发布时，重新审视 harness 通常是好的实践，剥离不再承重的部分并添加新部分来实现之前可能无法实现的更大能力。

从这项工作来看，我的信念是有趣的 harness 组合空间不会随着模型改进而缩小。相反，它会转移，AI 工程师的有趣工作是不断找到下一个新颖的组合。
