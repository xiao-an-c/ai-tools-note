# Excalidraw 图表创建器

生成 `.excalidraw` JSON 文件，**进行可视化论证**，而不仅仅是展示信息。

**安装配置：** 如果用户要求你设置此技能（渲染器、依赖等），请参阅 `README.md` 中的说明。

## 自定义

**所有颜色和品牌特定样式集中在一个文件中：** `references/color-palette.md`。在生成任何图表之前请先阅读它，并将其作为所有颜色选择的唯一权威来源——形状填充、描边、文字颜色、证据工件背景，一切都在其中。

要使此技能生成符合你自己品牌风格的图表，编辑 `color-palette.md` 即可。此文件中的所有其他内容都是通用设计方法论和 Excalidraw 最佳实践。

## 核心哲学

**图表应该论证，不是展示。**

图表不是格式化的文本。它是一种视觉论证，展示文字无法表达的关系、因果和流程。形状本身就应该承载含义。

**同构测试**：如果去掉所有文字，结构本身能否传达概念？如果不能，重新设计。

**教育测试**：观众能从这张图表中学到具体的东西吗，还是只看到标签框？好的图表能教人——它展示实际的格式、真实的事件名称、具体的示例。

## 深度评估（首先执行此步骤）

在设计之前，确定这张图表需要什么级别的细节：

### 简单/概念型图表
在以下情况使用抽象形状：
- 解释心智模型或哲学
- 受众不需要技术细节
- 概念本身就是抽象的（例如"关注点分离"）

### 综合/技术型图表
在以下情况使用具体示例：
- 绘制真实系统、协议或架构
- 图表将用于教学或讲解（例如 YouTube 视频）
- 受众需要了解事物的实际面貌
- 展示多种技术如何集成

**对于技术型图表，你必须包含证据工件**（见下文）。

## 研究强制令（针对技术型图表）

**在绘制任何技术内容之前，先研究实际的规范。**

如果你要绘制协议、API 或框架的图表：
1. 查阅实际的 JSON/数据格式
2. 找到真实的事件名称、方法名称或 API 端点
3. 理解各部分实际如何连接
4. 使用真实术语，而不是通用占位符

糟糕的做法："Protocol" → "Frontend"
好的做法："AG-UI streams events (RUN_STARTED, STATE_DELTA, A2UI_UPDATE)" → "CopilotKit renders via createA2UIMessageRenderer()"

**研究使图表既准确又有教育价值。**

## 证据工件

证据工件是证明图表准确性并帮助观众学习的具体示例。在技术型图表中包含它们。

**证据工件的类型**（选择与你的图表相关的类型）：

| 工件类型 | 何时使用 | 如何渲染 |
|----------|---------|---------|
| **代码片段** | API、集成、实现细节 | 深色矩形 + 语法着色文本（参见调色板中证据工件颜色） |
| **数据/JSON 示例** | 数据格式、Schema、Payload | 深色矩形 + 着色文本（参见调色板） |
| **事件/步骤序列** | 协议、工作流、生命周期 | 时间线模式（线 + 圆点 + 标签） |
| **UI 模拟** | 展示实际输出/结果 | 嵌套矩形模拟真实 UI |
| **真实输入内容** | 展示进入系统的内容 | 带有可见示例内容的矩形 |
| **API/方法名称** | 真实的函数调用、端点 | 使用文档中的实际名称，而非占位符 |

**示例**：对于展示流式协议的图表，你可能需要展示：
- 规范中的实际事件名称（而不是"事件 1"、"事件 2"）
- 展示如何连接的代码片段
- 流式数据的实际样貌

**示例**：对于展示数据转换管道的图表：
- 展示输入数据的样本（实际格式，而非"输入"）
- 展示输出数据的样本（实际格式，而非"输出"）
- 如相关，展示中间状态

核心原则：**展示事物的真实面貌**，而不只是名称。

## 多缩放架构

综合型图表同时工作在多个缩放级别。就像一张同时显示国界和街道名的地图。

### 第 1 级：摘要流程
简化的概览，一目了然地展示完整管道或流程。通常放在图表的顶部或底部。

*示例*：`Input → Processing → Output` 或 `Client → Server → Database`

### 第 2 级：区域边界
标记的区域将相关组件分组。这些视觉"房间"帮助观众理解哪些东西属于一起。

*示例*：按职责分组（后端 / 前端）、按阶段分组（设置 / 执行 / 清理）、或按团队分组（用户 / 系统 / 外部）

### 第 3 级：区域内的细节
每个区域内的证据工件、代码片段和具体示例。这是教育价值所在的地方。

*示例*：在"后端"区域内，你可能展示实际的 API 响应格式，而不只是一个标记为"API Response"的方框

**对于综合型图表，应包含所有三个级别。** 摘要提供上下文，区域负责组织，细节负责教学。

### 糟糕 vs 良好

| 糟糕（展示型） | 良好（论证型） |
|---------------|---------------|
| 5 个等大的方框加标签 | 每个概念的形状都反映其行为 |
| 卡片网格布局 | 视觉结构匹配概念结构 |
| 图标装饰文本 | 形状本身就是含义 |
| 所有东西用同一种容器 | 每个概念有不同的视觉词汇 |
| 所有东西都放在方框里 | 自由文本 + 选择性容器 |

### 简单 vs 综合（明确你需要哪种）

| 简单图表 | 综合图表 |
|---------|---------|
| 通用标签："Input" → "Process" → "Output" | 具体：展示输入/输出的实际样貌 |
| 命名方框："API"、"Database"、"Client" | 命名方框 + 实际请求/响应示例 |
| "Events" 或 "Messages" 标签 | 带有规范中真实事件/消息名称的时间线 |
| "UI" 或 "Dashboard" 矩形 | 展示实际 UI 元素和内容的模拟图 |
| 约 30 秒可以解释清楚 | 约 2-3 分钟的教学内容 |
| 观众学到结构 | 观众学到结构 **以及** 细节 |

**简单图表**适合抽象概念、快速概览，或当受众已经了解细节时使用。**综合图表**适用于技术架构、教程、教育内容，或当你希望图表本身就能教学时。

## 容器 vs 自由文本

**不是每段文字都需要形状包裹。** 默认使用自由文本。只有当容器有明确用途时才添加。

| 使用容器的情况... | 使用自由文本的情况... |
|-------------------|---------------------|
| 它是某个区域的焦点 | 它是标签或描述 |
| 它需要与其他元素进行视觉分组 | 它是辅助细节或元数据 |
| 箭头需要连接到它 | 它描述附近的东西 |
| 形状本身携带含义（如决策菱形等） | 排版本身就足以建立层级 |
| 它代表系统中的一个独立"事物" | 它是区域标题、副标题或注释 |

**排版即层级**：使用字号、字重和颜色来建立视觉层级，而非方框。28px 的标题不需要矩形包裹。

**容器测试**：对于每个带方框的元素，问"这作为自由文本是否也行？"如果可以，去掉容器。

## 设计流程（在生成 JSON 之前执行此步骤）

### 步骤 0：评估所需深度
首先，确定这需要：
- **简单/概念型**：抽象形状、标签、关系（心智模型、哲学）
- **综合/技术型**：具体示例、代码片段、真实数据（系统、架构、教程）

**如果是综合型**：先做研究。查阅实际的规范、格式、事件名称、API。

### 步骤 1：深入理解
阅读内容。对于每个概念，问：
- 这个概念**做什么**？（而不是它是什么）
- 概念之间存在什么关系？
- 核心的转换或流程是什么？
- **观众需要看到什么才能理解？**（而不是仅仅读到）

### 步骤 2：将概念映射到模式
对于每个概念，找到能反映其行为的视觉模式：

| 如果这个概念... | 使用这个模式 |
|----------------|-------------|
| 产生多个输出 | **扇出**（从中心辐射的箭头） |
| 合并多个输入为一个 | **汇聚**（漏斗、箭头合并） |
| 有层级/嵌套 | **树形**（线条 + 自由文本） |
| 是一系列步骤 | **时间线**（线 + 圆点 + 自由文本标签） |
| 循环或持续改进 | **螺旋/循环**（箭头回到起点） |
| 是抽象状态或上下文 | **云状**（重叠的椭圆） |
| 将输入转换为输出 | **流水线**（之前 → 处理 → 之后） |
| 比较两个事物 | **并排**（平行 + 对比） |
| 分为多个阶段 | **间隔/分隔**（区域之间的视觉分离） |

### 步骤 3：确保多样性
对于多概念图表：**每个主要概念必须使用不同的视觉模式**。不要使用统一的卡片或网格。

### 步骤 4：勾勒流程
在生成 JSON 之前，在脑海中追踪视线如何在图表中移动。应该有一个清晰的视觉故事。

### 步骤 5：生成 JSON
只有到了这一步才创建 Excalidraw 元素。**关于如何处理大型图表，见下文。**

### 步骤 6：渲染与验证（强制执行）
生成 JSON 后，你必须运行渲染-查看-修复循环，直到图表看起来正确。这不是可选项——完整流程见下方的**渲染与验证**部分。

## 大型/综合型图表策略

**对于综合型或技术型图表，你必须逐段构建 JSON。** 不要尝试在单次响应中生成整个文件。这是一个硬性约束——Claude Code 单次响应有约 32,000 token 的输出限制，一张综合图表轻松就能超出这个范围。即使不超出，一次性生成所有内容的质量也更差。逐段生成在任何方面都更好。

### 逐段工作流

**阶段 1：逐段构建**

1. **创建基础文件**，包含 JSON 包装器（`type`、`version`、`appState`、`files`）和第一段的元素。
2. **每次编辑添加一段。** 每段都有自己专门的生成过程——花时间仔细思考布局、间距以及如何与已有内容连接。
3. **使用描述性字符串 ID**（例如 `"trigger_rect"`、`"arrow_fan_left"`），使跨段引用可读。
4. **按段划分 seed 命名空间**（例如第 1 段使用 100xxx，第 2 段使用 200xxx），避免碰撞。
5. **在生成过程中更新跨段绑定。** 当新段的元素需要绑定到之前段的元素时（例如连接两段的箭头），同时编辑之前元素的 `boundElements` 数组。

**阶段 2：全局审查**

所有段就位后，通读完整 JSON 并检查：
- 跨段箭头是否在两端都正确绑定了？
- 整体间距是否平衡，还是某些段拥挤而其他段有过多留白？
- 所有 ID 和绑定引用的元素是否都存在？

在渲染之前修复任何对齐或绑定问题。

**阶段 3：渲染与验证**

现在运行渲染与验证部分中的渲染-查看-修复循环。这里能发现从 JSON 中不明显的视觉问题——重叠、裁切、不平衡的构图。

### 段边界

围绕图表计划中的自然视觉分组来规划你的段。一张典型的大型图表可能分为：

- **第 1 段**：入口点 / 触发器
- **第 2 段**：第一个决策或路由
- **第 3 段**：主要内容（hero 段——可能是最大的单段）
- **第 4-N 段**：剩余阶段、输出等

每段应该是独立可理解的：它自己的元素、内部箭头、以及对相邻段的任何跨段引用。

### 不要做的事

- **不要在一次响应中生成整个图表。** 你会触及输出 token 限制并产生被截断的、无效的 JSON。即使图表足够小能放下，分成段效果也更好。
- **不要使用编码 agent 来生成 JSON。** Agent 没有足够的技能规则上下文，协调开销会抵消任何收益。
- **不要写 Python 生成脚本。** 模板化和坐标计算看起来有帮助，但引入了一个间接层，使调试更困难。手工 JSON + 描述性 ID 更易维护。

## 视觉模式库

### 扇出（一对多）
中心元素，箭头辐射到多个目标。适用于：数据源、PRD、根本原因、中心枢纽。
```
        ○
       ↗
  □ → ○
       ↘
        ○
```

### 汇聚（多对一）
多个输入通过箭头合并到单个输出。适用于：聚合、漏斗、综合。
```
  ○ ↘
  ○ → □
  ○ ↗
```

### 树形（层级）
父子分支，用连接线和自由文本（不需要方框）。适用于：文件系统、组织架构、分类体系。
```
  label
  ├── label
  │   ├── label
  │   └── label
  └── label
```
使用 `line` 元素作为主干和分支，自由文本作为标签。

### 螺旋/循环（持续循环）
元素按顺序排列，箭头回到起点。适用于：反馈循环、迭代过程、演化。
```
  □ → □
  ↑     ↓
  □ ← □
```

### 云状（抽象状态）
不同大小的重叠椭圆。适用于：上下文、记忆、对话、心智状态。

### 流水线（转换）
输入 → 处理方框 → 输出，有清晰的前后对比。适用于：转换、处理、转换。
```
  ○○○ → [PROCESS] → □□□
  chaos              order
```

### 并排（对比）
两个平行结构，带视觉对比。适用于：前后对比、选项、权衡。

### 间隔/分隔（分离）
区域之间的视觉留白或分隔线。适用于：阶段变化、上下文重置、边界。

### 线条作为结构
使用线条（`line` 类型，不是箭头）作为主要结构元素，而非方框：
- **时间线**：垂直或水平线，间隔处有小圆点（10-20px 椭圆），旁边是自由文本标签
- **树形结构**：垂直主干线 + 水平分支线，带有自由文本标签（不需要方框）
- **分隔线**：细虚线用于分隔区域
- **流脊**：一个中心线，元素围绕它排列，而非连接方框

```
时间线:            树形:
  ●─── Label 1        │
  │                   ├── item
  ●─── Label 2        │   ├── sub
  │                   │   └── sub
  ●─── Label 3        └── item
```

线条 + 自由文本通常比方框 + 包含文本产生更干净的结果。

## 形状语义

根据概念代表什么来选择形状——或者干脆不用形状：

| 概念类型 | 形状 | 原因 |
|----------|------|------|
| 标签、描述、细节 | **无**（自由文本） | 排版建立层级 |
| 区域标题、注释 | **无**（自由文本） | 字号/字重就够了 |
| 时间线上的标记 | 小 `ellipse`（10-20px） | 视觉锚点，非容器 |
| 开始、触发、输入 | `ellipse` | 柔软、起源感 |
| 结束、输出、结果 | `ellipse` | 完成、目的地感 |
| 决策、条件 | `diamond` | 经典决策符号 |
| 过程、行动、步骤 | `rectangle` | 包含的动作 |
| 抽象状态、上下文 | 重叠 `ellipse` | 模糊、云状 |
| 层级节点 | 线 + 文本（无方框） | 通过线条建立结构 |

**规则**：默认不使用容器。只有当形状能承载含义时才添加。目标：少于 30% 的文本元素在容器内。

## 颜色即含义

颜色编码信息，不是装饰。每个颜色选择都应该来自 `references/color-palette.md`——语义形状颜色、文本层级颜色、证据工件颜色都在其中定义。

**关键原则：**
- 每个语义用途（开始、结束、决策、AI、错误等）都有特定的填充/描边对
- 自由文本使用颜色建立层级（标题、副标题、细节——各处于不同级别）
- 证据工件（代码片段、JSON 示例）使用自己的深色背景 + 着色文本方案
- 始终用较深的描边配较浅的填充以形成对比

**不要发明新颜色。** 如果一个概念不适合现有的语义类别，使用 Primary/Neutral 或 Secondary。

## 现代美学

对于干净、专业的图表：

### 粗糙度
- `roughness: 0` — 干净、利落的边缘。用于现代/技术型图表。
- `roughness: 1` — 手绘、有机感。用于头脑风暴/非正式图表。

**大多数专业场景默认为 0。**

### 描边宽度
- `strokeWidth: 1` — 细、优雅。适用于线条、分隔线、微妙的连接。
- `strokeWidth: 2` — 标准。适用于形状和主要箭头。
- `strokeWidth: 3` — 粗。谨慎使用以示强调（主流线、关键连接）。

### 不透明度
**所有元素始终使用 `opacity: 100`。** 用颜色、大小和描边宽度来创建层级，而非透明度。

### 小标记替代形状
使用小圆点（10-20px 椭圆）替代完整形状作为：
- 时间线标记
- 项目符号
- 连接节点
- 自由文本的视觉锚点

## 布局原则

### 通过尺度建立层级
- **Hero**：300×150 - 视觉锚点，最重要
- **Primary**：180×90
- **Secondary**：120×60
- **Small**：60×40

### 留白 = 重要性
最重要的元素周围有最多的空白（200px+）。

### 流向
引导视线：序列通常从左到右或从上到下，中心辐射型用径向。

### 连接是必须的
位置本身不展示关系。如果 A 与 B 相关，必须有箭头。

## 文本规则

**关键**：JSON 的 `text` 属性只包含可读的文字。

```json
{
  "id": "myElement1",
  "text": "Start",
  "originalText": "Start"
}
```

设置：`fontSize: 16`，`fontFamily: 3`，`textAlign: "center"`，`verticalAlign: "middle"`

## JSON 结构

```json
{
  "type": "excalidraw",
  "version": 2,
  "source": "https://excalidraw.com",
  "elements": [...],
  "appState": {
    "viewBackgroundColor": "#ffffff",
    "gridSize": 20
```

## 渲染与验证（强制执行）

你不能仅从 JSON 判断图表。在生成或编辑 Excalidraw JSON 后，你必须将其渲染为 PNG，查看图像，并修复你看到的问题——循环直到正确。这是工作流的核心部分，不是最终检查。

### 如何渲染

```bash
cd .claude/skills/excalidraw-diagram/references && uv run python render_excalidraw.py <path-to-file.excalidraw>
```

这会在 `.excalidraw` 文件旁边输出 PNG。然后使用 **Read 工具**查看 PNG。

### 循环

生成初始 JSON 后，运行此循环：

**1. 渲染与查看** — 运行渲染脚本，然后读取 PNG。

**2. 对照你的原始设计审计** — 在找 bug 之前，将渲染结果与你在步骤 1-4 中的设计进行比较。问：
- 视觉结构是否匹配你计划的概念结构？
- 每个段是否使用了你预期的模式（扇出、汇聚、时间线等）？
- 视线是否按照你的设计顺序在图表中流动？
- 视觉层级是否正确——hero 元素突出，辅助元素较小？
- 对于技术型图表：证据工件（代码片段、数据示例）是否可读且放置正确？

**3. 检查视觉缺陷：**
- 文字被容器裁切或溢出
- 文字或形状与其他元素重叠
- 箭头穿过元素而非绕过它们
- 箭头落在错误的元素上或指向空白处
- 标签悬浮不明（没有明确锚定到所描述的元素）
- 应该均匀间距的元素间距不均匀
- 某些段留白过多而其他段过于拥挤
- 文字在渲染尺寸下太小而无法阅读
- 整体构图感觉不平衡

**4. 修复** — 编辑 JSON 以解决你发现的所有问题。常见修复：
- 文字被裁切时加宽容器
- 调整 `x`/`y` 坐标修复间距和对齐
- 在箭头 `points` 数组中添加中间路径点以绕过元素
- 将标签重新定位到更靠近所描述元素的位置
- 调整元素大小以重新平衡各段的视觉权重

**5. 重新渲染与重新查看** — 再次运行渲染脚本并读取新的 PNG。

**6. 重复** — 持续循环，直到图表通过设计意图检查（步骤 2）和缺陷检查（步骤 3）。通常需要 2-4 次迭代。不要在第一轮没有关键 bug 后就停止——如果构图可以更好，就继续改进。

### 何时停止

循环在以下情况下完成：
- 渲染的图表与计划步骤中的概念设计匹配
- 没有文字被裁切、重叠或不可读
- 箭头正确路由并连接到正确的元素
- 间距一致且构图平衡
- 你愿意不带任何保留意见地展示给别人

### 首次设置
如果渲染脚本尚未设置：
```bash
cd .claude/skills/excalidraw-diagram/references
uv sync
uv run playwright install chromium
```

## 质量清单

### 深度与证据（技术型图表首先检查此项）
1. **研究已完成**：是否查阅了实际的规范、格式、事件名称？
2. **证据工件**：是否有代码片段、JSON 示例或真实数据？
3. **多缩放**：是否有摘要流程 + 区域边界 + 细节？
4. **具体优于抽象**：展示了真实内容，而非仅有标签方框？
5. **教育价值**：观众能否从中学到具体的东西？

### 概念性
6. **同构性**：每个视觉结构是否反映其概念的行为？
7. **论证性**：图表是否展示了文字无法表达的东西？
8. **多样性**：每个主要概念是否使用了不同的视觉模式？
9. **无统一容器**：是否避免了卡片网格和等大方框？

### 容器纪律
10. **最少容器**：任何带方框的元素是否可以改为自由文本？
11. **线条作为结构**：树形/时间线模式是否使用了线 + 文本而非方框？
12. **排版层级**：字号和颜色是否创建了视觉层级（减少对方框的需求）？

### 结构性
13. **连接**：每个关系都有箭头或线吗？
14. **流向**：有清晰的视觉路径供视线跟随吗？
15. **层级**：重要元素是否更大/更孤立？

### 技术性
16. **文本干净**：`text` 是否只包含可读文字？
17. **字体**：`fontFamily: 3`？
18. **粗糙度**：`roughness: 0`（除非要求手绘风格）？
19. **不透明度**：`opacity: 100`（无透明度）？
20. **容器比例**：少于 30% 的文本元素在容器内？

### 视觉验证（需要渲染）
21. **已渲染为 PNG**：图表已渲染并经过视觉检查
22. **无文字溢出**：所有文本都在容器内
23. **无元素重叠**：形状和文字没有意外重叠
24. **间距均匀**：相似元素有一致的间距
25. **箭头正确着陆**：箭头连接到目标元素，没有穿过其他元素
26. **导出尺寸下可读**：文本在渲染的 PNG 中清晰可读
27. **构图平衡**：没有大的空白区域或过度拥挤的区域
