# 可视化论证方法论

## 核心哲学

> Diagrams should ARGUE, not DISPLAY.

大多数 AI 生成的图表是"展示型"的：5 个等大的矩形框 + 标签 + 连线。信息全在文字里，图形只是装饰。

这个 Skill 追求的是"论证型"图表：**形状即含义**。一个 Fan-Out 结构天然表达"一个来源产生多个输出"，不需要额外解释。去掉所有文字，结构本身就能传达概念。

## 两个测试

**同构测试（The Isomorphism Test）**：

> If you removed all text, would the structure alone communicate the concept? If not, redesign.

视觉结构必须与概念结构同构。扇形展开的结构用来表达一对多关系，时间线结构用来表达序列——形状要"做"概念所做的事。

**教育测试（The Education Test）**：

> Could someone learn something concrete from this diagram, or does it just label boxes?

好图表教人东西。不只是"这里有个 API"，而是展示 API 返回的真实 JSON 长什么样。

## 深度评估——设计的第一个决策

SKILL.md 的第一步不是画图，是判断：

| | Simple/Conceptual | Comprehensive/Technical |
|--|-------------------|------------------------|
| **适用场景** | 心智模型、哲学概念 | 真实系统、协议、架构 |
| **元素** | 抽象形状 + 关系 | 具体示例 + 代码片段 + 真实数据 |
| **标签** | 通用标签（"Input" → "Process"） | 真实名称（`RUN_STARTED`, `STATE_DELTA`） |
| **耗时** | ~30 秒解释 | ~2-3 分钟教学内容 |

这个判断决定了后续所有路径：Simple 路径跳过研究、证据工件、多缩放；Comprehensive 路径全部执行。

## 研究强制令

技术图表在画之前必须先查资料：

> Before drawing anything technical, research the actual specifications.

这是"输入质量决定输出质量"的体现：

| 糟糕 | 良好 |
|------|------|
| "Protocol" → "Frontend" | "AG-UI streams events (RUN_STARTED, STATE_DELTA)" → "CopilotKit renders via createA2UIMessageRenderer()" |
| "Event 1", "Event 2" | 真实的事件名称 |
| "Input", "Output" | 真实的请求/响应格式 |

## 证据工件

Evidence Artifacts 是让图表从"示意图"升级为"教学工具"的关键。技术图表中必须包含具体证据：

| 工件类型 | 适用场景 | 渲染方式 |
|----------|---------|---------|
| 代码片段 | API、集成、实现细节 | 深色矩形 + 语法高亮文本 |
| JSON/数据示例 | 数据格式、Schema、Payload | 深色矩形 (`#1e293b`) + 绿色文本 (`#22c55e`) |
| 事件/步骤序列 | 协议、工作流、生命周期 | 时间线模式（线 + 圆点 + 标签） |
| UI 模拟 | 展示实际输出 | 嵌套矩形模拟真实界面 |
| 真实输入内容 | 展示系统输入 | 带有可见内容的矩形 |

核心原则：**展示事物的真实面貌**，而不只是名称。

## 多缩放架构

Comprehensive 图表同时工作在三个缩放层级：

```
┌─────────────────────────────────────────────────┐
│  Level 1: Summary Flow (Input → Process → Output) │
│                                                   │
│  ┌──────────────┐  ┌──────────────┐              │
│  │  Backend     │  │  Frontend    │   ← Level 2   │
│  │  ┌────────┐  │  │  ┌────────┐  │              │
│  │  │ API    │  │  │  │ Render │  │   ← Level 3   │
│  │  │ resp:  │  │  │  │ code:  │  │   (Detail)   │
│  │  │ {...}   │  │  │  │ ...    │  │              │
│  │  └────────┘  │  │  └────────┘  │              │
│  └──────────────┘  └──────────────┘              │
└─────────────────────────────────────────────────┘
```

- **Level 1 — Summary Flow**：全局概览，一眼看清完整流程
- **Level 2 — Section Boundaries**：分组区域，按职责/阶段/团队划分
- **Level 3 — Detail**：每个区域内的证据工件、代码片段、具体示例

类比：地图同时显示国界和街道名。

## 视觉模式库

每个概念映射到一个视觉模式——形状要"做"概念所做的事：

| 概念行为 | 视觉模式 | ASCII 示意 |
|----------|---------|-----------|
| 产生多个输出 | **Fan-Out** | `□ → ○ ↗ ○ ↘ ○` |
| 合并为一个输出 | **Convergence** | `○ ↘ ○ → □ ○ ↗` |
| 有层级/嵌套 | **Tree** | `├── item └── item` |
| 步骤序列 | **Timeline** | `●─── Label 1 │ ●─── Label 2` |
| 循环/迭代 | **Spiral/Cycle** | `□ → □ ↑ ↓ □ ← □` |
| 抽象状态/上下文 | **Cloud** | 重叠的椭圆 |
| 输入→输出转换 | **Assembly Line** | `○○○ → [PROCESS] → □□□` |
| 两者对比 | **Side-by-Side** | 平行结构 + 视觉对比 |
| 阶段分隔 | **Gap/Break** | 留白或分割线 |

关键约束：**每个主要概念必须使用不同的视觉模式**。这直接禁止了最常见的"卡片网格"布局。

## 容器纪律

默认使用自由文本，不是每个标签都需要方框：

| 用容器 | 用自由文本 |
|--------|-----------|
| 是某个 section 的焦点 | 是标签或描述 |
| 需要与其他元素视觉分组 | 是辅助细节 |
| 箭头需要连接到它 | 描述附近的其他元素 |
| 形状本身携带含义（如菱形=决策） | 是 section 标题/注释 |
| 代表系统中的独立"事物" | 排版本身就足以建立层级 |

**硬约束**：少于 30% 的文本元素应该在容器内。

用排版替代方框：28px 的标题不需要矩形包裹，字号、字重、颜色就能建立层级。

## 形状语义

| 概念类型 | 形状 | 原因 |
|----------|------|------|
| 标签、描述、细节 | 无（自由文本） | 排版建立层级 |
| 时间线上的标记 | 小椭圆（10-20px） | 视觉锚点，非容器 |
| 开始、触发、输入 | `ellipse` | 柔软、起源感 |
| 结束、输出、结果 | `ellipse` | 完成、目的地感 |
| 决策、条件 | `diamond` | 经典决策符号 |
| 过程、行动、步骤 | `rectangle` | 包含的动作 |
| 抽象状态、上下文 | 重叠 `ellipse` | 模糊、云状 |
| 层级节点 | 线 + 文本（无方框） | 通过线条建立结构 |

## 27 项质量清单

Quality Checklist 本质上是一个自然语言写成的验收测试套件，分为 5 组：

**Depth & Evidence**（5 项）— 功能测试：
- 是否做了研究？是否有证据工件？是否有多缩放？是否用了具体内容而非抽象标签？是否有教育价值？

**Conceptual**（4 项）— 设计评审：
- 同构测试通过？图表展示了文字无法表达的东西？每个概念用了不同模式？没有统一容器网格？

**Container Discipline**（3 项）— 代码规范：
- 可以去掉容器的都去掉了？Tree/Timeline 用了线+文本？排版建立了层级？

**Structural**（3 项）— 集成测试：
- 每个关系都有箭头？有清晰的视觉路径？重要元素更大/更孤立？

**Technical**（5 项）— 单元测试：
- text 字段干净？fontFamily: 3？roughness: 0？opacity: 100？容器比例 <30%？

**Visual Validation**（7 项）— E2E 测试（需渲染后执行）：
- 已渲染？无文字溢出？无元素重叠？间距均匀？箭头连接正确？文本可读？构图平衡？

最后一组必须渲染成图片才能检查——文字是否被容器裁切、元素是否重叠、箭头是否穿过其他元素，这些问题从 JSON 字面值上看不出来。这就是渲染管线存在的根本原因。
